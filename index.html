읽는 방법

처음부터 모두 암기할 필요는 없습니다. 왼쪽 목차에서 지금 작성 중인 코드와 관련된 장을 찾아보고, 예제를 프로젝트 코드에 한 번 적용해 보는 방식이 가장 빠릅니다.

핵심 기준문법이 짧다는 것보다, 잘못된 상태를 만들기 어렵고 코드의 책임이 명확한지가 더 중요합니다.

CHAPTER 01

주 생성자와 val/var

웹 애플리케이션의 클래스는 대개 Service가 Repository를 필요로 하는 것처럼 다른 객체에 의존합니다. Java에서는 필드와 생성자를 따로 작성하지만, Kotlin은 클래스 이름 옆의 주 생성자(primary constructor)에서 둘을 함께 선언합니다.

Kotlin은 생성자 매개변수와 프로퍼티 선언을 한곳에 모을 수 있습니다. Spring의 생성자 주입과 특히 잘 맞습니다.

@Service
class DiaryService(
    private val diaryRepository: DiaryRepository,
)

val은 다른 값을 다시 대입할 수 없고, var는 다시 대입할 수 있습니다. 기본은 val로 시작하세요.

val title = "오늘의 일기"
var editCount = 0
editCount += 1
val은 깊은 불변성이 아니다val items = mutableListOf<String>()에서는 items가 가리키는 리스트를 교체할 수 없을 뿐, 리스트 내용은 바꿀 수 있습니다.

생성자에 val이나 var 없이 이름만 쓰면 생성 중에만 사용할 수 있는 매개변수이고, 객체의 프로퍼티로 남지 않습니다.

class Example(
    name: String,           // 생성자 매개변수일 뿐
    val title: String,      // 읽기 전용 프로퍼티
    var editCount: Int,     // 변경 가능한 프로퍼티
) {
    val displayName = "$name: $title"
}

Spring에서의 습관

  • 의존성은 private val 생성자 주입으로 둡니다.
  • 필드 주입과 불필요한 lateinit은 피합니다.
  • 클래스 외부에 공개할 이유가 없다면 접근 제한자를 명시합니다.

CHAPTER 02

Null 가능성을 타입으로 표현하기

Java에서는 메서드 선언만 보고 반환값이 null인지 확신하기 어렵습니다. Kotlin은 “값이 없을 수 있음”을 ?로 타입에 기록하고, 처리하지 않으면 컴파일을 막습니다. 런타임의 NPE를 코드 작성 시점의 선택으로 바꾸는 셈입니다.

String과 String?은 서로 다른 타입입니다. null 가능성을 숨기지 않고 함수 계약에 드러냅니다.

val requiredTitle: String = "제목"
val optionalMemo: String? = null

val length = optionalMemo?.length       // null이면 null
val text = optionalMemo ?: "메모 없음"  // null이면 기본값

Repository 조회 결과를 처리하는 흔한 코드입니다.

val diary = diaryRepository.findById(id)
    ?: throw DiaryNotFoundException(id)
!!는 마지막 수단value!!는 컴파일러의 보호를 해제하고 null이면 NPE를 발생시킵니다. 왜 절대 null이 아닌지 타입이나 흐름으로 증명하는 편이 좋습니다.

HTTP 요청에서 null과 빈 문자열은 다르다

data class SearchRequest(
    val keyword: String?,
)

// null: 필드가 없거나 명시적으로 null
// "": 값은 있지만 비어 있음
val keyword = request.keyword?.trim()?.takeIf { it.isNotEmpty() }

필수 입력은 애초에 non-null 타입으로 선언하고 validation으로 오류를 설명하는 편이 좋습니다. 모든 필드를 습관적으로 nullable로 만들면 이후 코드 전체가 null 처리로 퍼집니다.

유용한 도구

value?.let { use(it) }          // null이 아닐 때만 실행
value?.takeIf { it.isValid() }  // 조건을 만족하면 값, 아니면 null
requireNotNull(value)           // 인자가 null이면 예외
checkNotNull(value)             // 현재 상태가 null이면 예외

CHAPTER 03

함수, 기본 인자와 표현식

Kotlin 함수는 fun 이름(매개변수): 반환타입 순서입니다. Java와 달리 반환 타입이 함수 이름 뒤에 오며, 반환 타입이 명확하면 생략할 수도 있습니다. 공개 API와 Service 함수에서는 계약을 쉽게 읽도록 반환 타입을 적는 편이 좋습니다.

본문이 하나의 표현식이면 =로 간결하게 쓸 수 있습니다.

@GetMapping
fun getDiaries(): List<Diary> =
    diaryService.getDiaries()

if, when, try, throw도 값을 만드는 표현식입니다.

val label = when {
    title.isBlank() -> "제목 없음"
    title.length > 100 -> "너무 긴 제목"
    else -> "정상"
}

기본 인자와 이름 있는 인자

data class Diary(
    val id: UUID = newUuidV7(),
    val title: String,
    val content: String,
)

Diary(title = "오늘", content = "Kotlin 공부")
읽기 쉬움이 우선로직이 길거나 분기와 부수 효과가 많다면 억지로 단일 표현식 함수로 만들지 말고 블록 본문을 사용하세요.

Unit과 Nothing

Unit은 의미 있는 반환값이 없다는 뜻으로 Java의 void와 비슷합니다. Nothing은 함수가 정상적으로 돌아오지 않는다는 뜻으로, 항상 예외를 던지는 함수 등에 사용됩니다.

fun logCreated(id: UUID): Unit {
    logger.info { "created: $id" }
}

fun notFound(id: UUID): Nothing =
    throw DiaryNotFoundException(id)

CHAPTER 04

data class와 copy

요청 DTO나 응답 DTO처럼 “무슨 행동을 하는가”보다 “어떤 값들을 담는가”가 중요한 객체가 많습니다. 이런 값 중심 객체의 반복 코드를 줄이는 선언이 data class입니다.

data class는 값 중심 객체에 필요한 equals, hashCode, toString, copy, 구조 분해 함수를 생성합니다.

data class DiaryResponse(
    val id: UUID,
    val title: String,
)

val renamed = diary.copy(title = "수정된 제목")

copy()는 기존 객체의 일부 값을 바꾼 새 객체를 만드는 기능입니다. DB 행으로부터 최초 객체를 만드는 복원 함수와는 목적이 다릅니다.

copy는 객체를 수정하지 않는다diary.copy(title = "새 제목")은 기존 diary를 그대로 두고 새 Diary를 반환합니다. 따라서 반환값을 받지 않으면 아무 변화도 일어나지 않습니다.
동작의미예시
생성새 엔티티 발급Diary.create(...)
복원DB의 기존 상태 재구성Diary.restore(...)
복사기존 객체를 기준으로 변경diary.copy(title = ...)
JPA 엔티티에서는 주의자동 생성되는 동등성 비교와 프록시·지연 로딩이 충돌할 수 있습니다. 현재 프로젝트처럼 jOOQ를 사용한다면 이 제약은 상대적으로 적습니다.

또한 data class의 동등성은 주 생성자에 선언된 프로퍼티를 기준으로 합니다. ID만 같으면 같은 엔티티인지, 모든 값이 같아야 같은 값인지에 따라 도메인 객체에 적합한지 판단해야 합니다.

CHAPTER 05

init, require, check

주 생성자에는 실행문을 직접 쓸 수 없습니다. 생성자 매개변수를 받아 계산하거나 검증해야 할 때 init 블록을 사용합니다. 여러 개를 선언하면 코드에 적힌 순서대로 프로퍼티 초기화와 함께 실행됩니다.

init은 주 생성자 호출 중 실행되는 초기화 블록입니다. 객체가 태어나는 순간 반드시 만족해야 하는 불변 조건을 검사할 수 있습니다.

data class Diary(
    val id: UUID,
    val title: String,
) {
    init {
        require(id.version() == 7) {
            "Diary id는 UUID v7이어야 합니다: $id"
        }
        require(title.isNotBlank()) {
            "제목은 비어 있을 수 없습니다"
        }
    }
}
함수의미예외
require호출자가 넘긴 인자가 잘못됨IllegalArgumentException
check현재 객체·프로그램 상태가 잘못됨IllegalStateException
error도달하면 안 되는 상태IllegalStateException
좋은 불변 조건저장 여부나 특정 화면과 무관하게, 이 타입이 존재하는 동안 언제나 참이어야 하는 규칙입니다.

예외를 던지는 검증이 항상 정답은 아니다

프로그래머가 잘못된 객체를 만드는 상황에는 require가 잘 맞습니다. 반면 사용자가 입력을 틀리는 것이 정상적인 흐름이고 여러 오류를 한꺼번에 보여줘야 한다면 요청 DTO의 Bean Validation이나 명시적인 결과 타입이 더 적합합니다.

CHAPTER 06

companion object

어떤 함수는 특정 Diary 한 개의 행동이 아니라 “Diary를 만드는 방법”처럼 클래스 전체와 관련됩니다. 그렇다고 파일 최상위에 두면 소속이 흐려질 수 있습니다. 이때 클래스에 하나만 존재하는 동반 객체에 둘 수 있습니다.

클래스 인스턴스 없이 클래스 이름을 통해 접근할 함수와 값을 둡니다. Java의 static과 사용감은 비슷하지만 실제로는 클래스에 연결된 객체입니다.

class Diary private constructor(
    val id: UUID,
    val title: String,
) {
    companion object {
        const val MAX_TITLE_LENGTH = 100

        fun create(title: String): Diary =
            Diary(id = newUuidV7(), title = title)
    }
}

val diary = Diary.create("오늘")

언제 factory를 만드는가?

  • 생성 과정에 이름을 붙이고 싶을 때
  • 생성 방식이 여러 개이고 규칙이 다를 때
  • 생성자를 감추고 올바른 생성 경로만 공개하고 싶을 때

create는 신규 ID와 시간을 만들고, restore는 저장된 ID와 시간을 유지하는 식으로 의도를 구분할 수 있습니다. 단순한 프로젝트라면 공개 생성자와 init만으로 시작해도 충분합니다.

Spring Bean과는 다른 것companion object는 Kotlin/JVM 차원의 단일 객체이지 Spring이 관리하는 Bean이 아닙니다. Repository나 다른 Bean을 주입받아야 하는 비즈니스 로직은 Service에 두는 편이 자연스럽습니다.

CHAPTER 07

컬렉션을 변환하는 함수들

Java에서 반복문을 돌며 결과 리스트에 직접 추가하던 코드를 Kotlin에서는 “무엇을 원하는지” 나타내는 연산으로 표현할 수 있습니다. 원본 컬렉션은 그대로 두고 새로운 결과를 반환하는 함수가 대부분입니다.

Repository 결과를 응답 DTO로 바꾸는 코드에서 특히 자주 사용합니다.

val responses = diaries
    .filter { it.title.isNotBlank() }
    .map { diary ->
        DiaryResponse(id = diary.id, title = diary.title)
    }
함수용도
map각 원소를 다른 값으로 변환
filter조건을 만족하는 원소만 선택
firstOrNull첫 원소를 찾고 없으면 null
associateBy특정 값을 key로 Map 생성
groupBy기준값으로 그룹화
any / all / none조건의 존재·전체·부재 검사

일반 컬렉션과 Sequence의 차이

List에 여러 연산을 이어 붙이면 각 단계가 전체 원소를 처리하고 중간 컬렉션을 만듭니다.

val titles = diaries
    .filter { it.content.isNotBlank() } // 조건에 맞는 List 생성
    .map { it.title }                   // 제목만 담은 새 List 생성
    .take(3)                            // 앞의 3개를 담은 List 생성

반면 asSequence()를 호출하면 연산을 즉시 수행하지 않고 작업 순서만 구성합니다. 마지막에 toList()처럼 결과가 필요해질 때, 원소 하나를 filter → map 순서로 처리합니다.

val titles = diaries
    .asSequence()
    .filter { it.content.isNotBlank() }
    .map { it.title }
    .take(3)
    .toList()

이 예에서는 제목 3개를 찾으면 나머지 원소를 확인하지 않아도 되고, 단계마다 중간 List도 만들지 않습니다. 따라서 원소가 많거나 변환 단계가 여러 개거나 take, first처럼 중간에 멈출 수 있는 연산에서는 유리할 수 있습니다.

그렇다고 Sequence가 항상 빠른 것은 아니다Sequence는 원소마다 iterator를 거치고 지연 연산을 호출하는 비용이 있습니다. 원소가 몇 개뿐이거나 map 한 번만 수행한다면 중간 List를 줄이는 이점보다 이 추가 비용이 더 클 수 있습니다. 우선 일반 컬렉션 함수를 사용하고, 큰 컬렉션의 긴 변환 파이프라인이 실제 병목일 때 측정한 뒤 Sequence를 고려하세요.
간단한 판단 기준diaries.map { ... }처럼 짧으면 List를 그대로 사용합니다. 수천 개 이상의 원소에 여러 변환을 연결하거나 일부 결과만 찾고 바로 멈출 수 있다면 asSequence()를 검토합니다. DB 조회라면 Sequence로 처리하기 전에 SQL의 WHERE와 LIMIT으로 데이터 자체를 줄이는 것이 먼저입니다.

CHAPTER 08

스코프 함수: 적게, 의도가 보이게

스코프 함수는 객체를 잠시 람다의 문맥 안에 넣어 연속 작업을 표현합니다. 새로운 능력을 제공하는 문법은 아니며, 평범한 지역 변수로 쓸 코드를 특정 모양으로 정리하는 도구입니다. 그래서 이름보다 두 질문이 중요합니다: 객체를 it과 this 중 무엇으로 부르는가, 그리고 객체 자체와 계산 결과 중 무엇을 반환하는가?

함수객체 이름반환값대표 용도
letit람다 결과null 처리·변환
runthis람다 결과객체로 계산
applythis객체 자체객체 설정
alsoit객체 자체로깅 등 부가 작업
withthis람다 결과비-null 객체로 여러 작업
return diaryRepository.create(diary)
    .also { saved ->
        logger.info { "Diary 저장 완료: ${saved.id}" }
    }

null 처리에서 자주 보는 let

val result = request.keyword?.let { keyword ->
    diaryRepository.search(keyword)
} ?: emptyList()

keyword가 null이 아니면 검색 결과를, null이면 빈 목록을 만듭니다. 단순히 null 검사만 필요하다면 if (keyword != null)이 더 명확할 수도 있습니다.

중첩하지 않기it과 this가 누구인지 잠시 생각해야 한다면 일반 지역 변수와 명시적인 코드가 더 좋습니다.

CHAPTER 09

확장 함수

DTO 변환 같은 코드를 Controller에 계속 쓰면 HTTP 처리와 객체 조립이 뒤섞입니다. 그렇다고 단순 변환만 하는 클래스를 매번 만들기는 번거롭습니다. 확장 함수는 이런 작고 응집된 변환에 이름을 붙이는 방법입니다.

기존 타입을 수정하지 않고 그 타입의 함수처럼 호출할 기능을 정의합니다.

fun CreateDiaryRequest.toDiary(): Diary =
    Diary(
        title = title.trim(),
        content = content.trim(),
    )

val diary = request.toDiary()

확장 함수는 실제 멤버를 추가하지 않으며 컴파일 시점의 타입을 기준으로 호출됩니다. DTO → 도메인 → 응답 변환처럼 경계가 분명한 매핑에서 특히 유용합니다.

// 실제로는 이 형태의 일반 함수와 비슷하게 컴파일됩니다.
fun toDiary(request: CreateDiaryRequest): Diary = ...
배치 기준한 타입에서만 쓰면 그 타입 가까이에, 여러 계층에서 공유하면 의미 있는 별도 파일에 둡니다. 모든 것을 Extensions.kt 하나에 모으지 마세요.

CHAPTER 10

sealed 타입과 value class

앞 장들에서는 값 하나가 유효한지를 다뤘습니다. 이제 함수가 가질 수 있는 결과의 종류와, 같은 원시 타입을 서로 다른 개념으로 구별하는 방법을 봅니다. 둘 다 컴파일러가 실수를 미리 잡게 만드는 문법입니다.

결과의 경우의 수: sealed interface

sealed interface CreateDiaryResult {
    data class Success(val diary: Diary) : CreateDiaryResult
    data object Duplicate : CreateDiaryResult
}

val response = when (val result = service.create(request)) {
    is CreateDiaryResult.Success -> ResponseEntity.ok(result.diary)
    CreateDiaryResult.Duplicate -> ResponseEntity.status(409).build()
}

가능한 하위 타입이 제한되므로 when에서 빠진 경우를 컴파일러가 알려줍니다.

모든 Service 결과를 sealed 타입으로 만들 필요는 없습니다. 성공하거나 예외를 던지는 단순 CRUD에는 과할 수 있고, 성공·중복·승인 대기처럼 호출자가 정상적으로 나눠 처리할 결과가 여러 개일 때 유용합니다.

원시 타입에 의미 부여: value class

@JvmInline
value class DiaryId(val value: UUID) {
    init {
        require(value.version() == 7)
    }
}

UserId와 DiaryId가 모두 UUID여도 서로 섞이지 않습니다. 다만 Jackson과 jOOQ 경계에는 변환 설정이 필요할 수 있으므로 복잡도를 감수할 가치가 있을 때 도입합니다.

CHAPTER 12

Diary의 UUID v7 규칙은 어디에 둘까?

검증 코드를 어디에 둘지는 문법 문제가 아니라 규칙의 범위 문제입니다. Controller에 두면 다른 호출 경로가 우회할 수 있고, Repository에 두면 저장 전까지 잘못된 객체가 존재할 수 있습니다. 먼저 그 규칙이 언제 참이어야 하는지 문장으로 적어봅니다.

“모든 Diary ID는 언제나 UUID v7이다”가 규칙이면 객체 생성 시 검증합니다.

data class Diary(
    val id: UUID = Generators.timeBasedEpochGenerator().generate(),
    val title: String,
    val content: String,
    val createdAt: Instant = Instant.now(),
) {
    init {
        require(id.version() == 7) {
            "Diary id는 UUID v7이어야 합니다: $id"
        }
    }
}

Repository에서만 검사하면 잘못된 Diary가 Service 내부에는 존재할 수 있습니다. Repository 검증은 중복 ID, DB 컬럼 제한, 동시성처럼 저장 시점에만 알 수 있는 규칙에 적합합니다.

판단 질문DB에 저장하지 않는 Diary도 UUID v7이어야 하는가? “예”라면 객체 규칙, “새로 저장할 때만”이라면 생성 정책 또는 저장 경계의 규칙입니다.

현재 단계에서는 init 검증과 요청 DTO 분리가 단순하고 견고합니다. 생성 방식이 늘어난 뒤에 create/restore factory를 고려해도 늦지 않습니다.

CHAPTER 13

테스트는 책임의 소유자 곁에

테스트 파일은 “누가 이 규칙을 보장하는가?”를 기준으로 찾으면 됩니다. 객체 생성자가 UUID를 거부한다면 그 행동의 소유자는 Diary이고, Service는 이미 유효한 Diary를 받아 저장 흐름을 조율합니다.

UUID 불변 조건은 DiaryServiceTest가 아니라 DiaryTest에서 검증합니다.

class DiaryTest {
    @Test
    fun `UUID v7이 아니면 생성할 수 없다`() {
        assertFailsWith<IllegalArgumentException> {
            Diary(
                id = UUID.randomUUID(), // v4
                title = "제목",
                content = "내용",
            )
        }
    }

    @Test
    fun `기본 ID는 UUID v7으로 생성된다`() {
        val diary = Diary(title = "제목", content = "내용")
        assertEquals(7, diary.id.version())
    }
}
테스트확인할 책임
DiaryTest생성 규칙과 불변 조건
DiaryServiceTest업무 흐름과 Repository 협력
DiaryControllerTestHTTP, JSON, 상태 코드와 validation
DiaryRepositoryTestSQL 매핑, 저장과 조회
객체 테스트가 필요한 때단순 DTO의 프로퍼티나 Kotlin이 생성한 equals를 다시 테스트하지 않습니다. 객체가 직접 가진 규칙과 동작이 있을 때 테스트합니다.

테스트 이름도 구현 세부사항보다 보장하는 규칙을 문장으로 적는 편이 좋습니다. 예를 들어 “require가 IllegalArgumentException을 던진다”보다 “UUID v7이 아니면 Diary를 생성할 수 없다”가 리팩터링 후에도 의미가 유지됩니다.

CHAPTER 14

Kotlin 로깅과 @Slf4j

애플리케이션 코드는 실행 중 상태를 관찰할 수 있어야 하지만, println은 레벨·형식·출력 위치를 운영 환경에 맞게 제어하기 어렵습니다. 로깅 facade를 사용하면 코드는 같은 API를 호출하면서 환경별 설정으로 출력 방식을 바꿀 수 있습니다.

private val logger = KotlinLogging.logger {}

@Service
class DiaryService(...) {
    fun createDiary(diary: Diary) {
        logger.info { "Diary 생성: ${diary.id}" }
    }
}

Java의 Lombok @Slf4j는 어노테이션이 간단한 것이 아니라 컴파일 과정에서 Logger 필드를 생성해 숨긴 것입니다. Kotlin Logging은 일반 Kotlin 코드로 로거를 명시하며 람다 메시지는 해당 로그 레벨이 비활성화되면 문자열 계산을 피할 수 있습니다.

레벨대표 용도
debug개발·진단에 필요한 상세 흐름
info중요한 정상 업무 이벤트
warn처리는 가능하지만 살펴볼 비정상 상황
error요청 실패나 운영 조치가 필요한 오류
민감 정보 주의Diary의 content 전체, 인증 정보, 개인 정보를 로그에 남기지 마세요. 식별자와 처리 결과처럼 운영에 필요한 최소 정보만 남깁니다.

CHAPTER 15

Kotest와 JUnit 5 성능 이해

테스트 실행 창에 표시되는 총 시간은 테스트 함수 본문의 시간과 같지 않습니다. 소스 컴파일, Gradle daemon, 별도 테스트 JVM, 테스트 탐색을 거친 뒤에야 Mockito 테스트 본문이 실행됩니다. 수 밀리초짜리 테스트 하나에서는 이 고정비가 거의 전부로 보일 수 있습니다.

Kotest와 JUnit Jupiter는 모두 JUnit Platform에 연결되는 별도의 TestEngine입니다. 짧은 mock 테스트에서는 테스트 본문보다 Gradle/JVM 기동, Kotlin 컴파일, 엔진 초기화와 테스트 탐색 비용이 더 크게 보일 수 있습니다.

Gradle / IntelliJ
       ↓
JUnit Platform
   ├─ JupiterTestEngine
   └─ KotestTestEngine

Kotest 5.x에는 extension classpath 탐색과 source reference 계산 등 시작 비용에 영향을 줄 요소가 있었습니다. isolation을 InstancePerTest로 바꾼 경우 spec 초기화가 반복될 수도 있습니다. 하지만 10초 전체를 Kotest 탓으로 단정하려면 구간을 측정해야 합니다.

.\gradlew test --tests "*DiaryServiceTest" --info
  • compileTestKotlin이 길면 컴파일·cold cache 문제입니다.
  • Test Executor 전이 길면 JVM·classpath·탐색 비용입니다.
  • 테스트 구간이 길면 extension, isolation 또는 테스트 본문을 봅니다.

현재처럼 Mockito 기반의 짧은 단위 테스트이고 Kotest의 property testing이나 DSL을 활용하지 않는다면 JUnit 5를 유지하는 것이 실용적입니다.

공정하게 비교하기둘 다 같은 실행기(Gradle 또는 IntelliJ)로 실행하고 첫 실행끼리, warm cache 실행끼리 비교하세요. 테스트 프레임워크를 바꾸면서 의존성이나 Spring 애노테이션까지 달라지면 프레임워크 자체의 차이를 측정한 것이 아닙니다.

추천 학습 순서와 체크리스트

아래 순서는 문법 난이도순이 아니라 Diary 프로젝트에서 효과를 바로 확인하기 좋은 순서입니다. 한 항목씩 실제 코드를 바꾸고 테스트가 설명하는 책임도 함께 정리해 보세요.

  1. 생성자 주입과 val을 기본 습관으로 만듭니다.
  2. String?, ?., ?:로 null 흐름을 명확히 합니다.
  3. 요청 DTO와 도메인 객체를 분리합니다.
  4. init과 require로 Diary 불변 조건을 표현합니다.
  5. map, filter, firstOrNull로 조회 결과를 변환합니다.
  6. DTO 변환을 작은 함수나 확장 함수로 분리합니다.
  7. 경우의 수가 늘 때 sealed 타입을 고려합니다.
  8. 타입 혼동이 실제 문제가 될 때 value class를 도입합니다.
