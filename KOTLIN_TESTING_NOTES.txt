Kotlin 웹 애플리케이션 테스트 전략 노트
=========================================

목적
----
- 기존 DiaryService 단위 테스트와 Service + Repository 통합 테스트의 역할을 정리한다.
- 테스트 종류 자체보다 실제로 잡아야 하는 위험을 기준으로 테스트를 선택한다.
- 로컬과 CI에서 동일하게 실행할 수 있는 PostgreSQL 테스트 환경을 구성한다.


1. 현재 DiaryService 단위 테스트의 한계
=======================================

현재 DiaryService는 대부분 Repository 호출을 전달하는 역할을 한다.

    fun findAll(): List<Diary> =
        diaryRepository.findAll()

이런 Service를 Mock Repository로 테스트하면 주로 다음 내용만 확인한다.

    whenever(diaryRepository.findAll()).thenReturn(diaries)

    val result = diaryService.findAll()

    assertEquals(diaries, result)
    verify(diaryRepository).findAll()

이 테스트는 테스트 코드에서 지정한 Mock 결과가 그대로 반환되는지 확인한다.
실제 SQL, jOOQ 매핑, DB 스키마, 정렬 및 페이지 경계는 검증하지 않는다.

따라서 결론은 "웹 개발에서 단위 테스트가 의미 없다"가 아니라 다음과 같다.

    로직이 없는 계층을 Mock으로 격리해 테스트하는 것은 가치가 작다.

Service에 다음과 같은 독립적인 업무 규칙이 생기면 단위 테스트 가치가 커진다.
- 권한 판단
- 상태 전이
- 금액이나 날짜 계산
- 여러 조건에 따른 분기
- 외부 시스템 실패에 대한 재시도 또는 복구 정책


2. 통합 테스트 전환이 타당한 이유
=================================

Diary 프로젝트에서 실제 버그 가능성이 높은 부분은 Repository와 DB 경계다.

    .where(DIARIES.ID.lessThan(cursorId))
    .orderBy(DIARIES.ID.desc())
    .limit(size + 1)

검증해야 할 실제 동작:
- jOOQ 쿼리가 PostgreSQL에서 올바르게 실행되는가?
- DB 레코드가 Diary로 올바르게 매핑되는가?
- Flyway 마이그레이션으로 테스트 스키마를 만들 수 있는가?
- size + 1 조회로 hasNext가 올바르게 계산되는가?
- 다음 페이지에서 데이터가 누락되거나 중복되지 않는가?
- 빈 데이터와 마지막 페이지가 올바르게 처리되는가?

Mock Repository는 이 문제들을 검증하지 못한다. 현재 Service에는 별도 로직이
거의 없더라도 실제 사용 경로를 검증하려면 Service부터 PostgreSQL까지 연결하는
통합 테스트가 더 정확하고 유용하다.

테스트 이름도 성격을 드러내도록 변경하는 편이 좋다.

    DiaryServiceTest
        + DiaryServiceIntegrationTest

현재 통합 테스트 범위는 다음과 같다.

    DiaryService -> DiaryRepository -> jOOQ -> PostgreSQL

기존 Mock 단위 테스트는 처음에는 남겨 두고, 통합 테스트와 완전히 중복되는
단순 위임 검증은 이후 제거할 수 있다. Service에 업무 규칙이 생기면 해당 규칙은
빠른 단위 테스트로 계속 검증한다.


3. Testcontainers를 권장하는 이유
=================================

CI까지 고려하면 테스트 전용 PostgreSQL을 Testcontainers로 실행하는 방식이
가장 재현성이 높다.

장점:
- 로컬과 CI에서 같은 PostgreSQL 이미지와 버전을 사용한다.
- 테스트마다 깨끗하고 예측 가능한 환경을 준비할 수 있다.
- 개발용 데이터와 테스트 데이터가 섞이지 않는다.
- application.yaml의 localhost:5432에 의존하지 않는다.
- 임의의 호스트 포트를 사용하므로 개발용 PostgreSQL과 충돌하지 않는다.
- Flyway 마이그레이션을 실제 빈 DB에서 검증한다.

현재 로컬 Compose DB가 실행 중이어도 Testcontainers는 별도 컨테이너를 사용한다.

    개발용 Compose PostgreSQL       localhost:5432
    테스트용 Testcontainers DB     localhost:임의 포트

컨테이너가 하나 더 실행되지만 개발 데이터 삭제나 테스트 간 오염을 막을 수 있다.


4. 기존 로컬 Compose DB를 테스트에 사용하지 않는 이유
=====================================================

기존 DB를 재사용하면 시작 시간이 짧다는 장점이 있지만 다음 문제가 생긴다.

- 개발 데이터에 따라 테스트 성공 여부가 달라질 수 있다.
- 테스트 정리 코드가 개발 데이터를 삭제할 수 있다.
- 이전 실행의 데이터가 남아 테스트가 서로 영향을 줄 수 있다.
- CI에서는 결국 별도의 DB 설정이 필요하다.
- 로컬 테스트와 CI 테스트의 실행 방식이 달라진다.
- 깨끗한 DB에 Flyway가 정상 적용되는지 확인하기 어렵다.

특히 다음 코드는 개발 DB에 연결되면 위험하다.

    @BeforeEach
    fun cleanDatabase() {
        dsl.deleteFrom(DIARIES).execute()
    }

테스트 편의를 위해 개발 DB와 테스트 DB의 경계를 흐리지 않는다.


5. 필요한 테스트 의존성
======================

Spring Boot의 의존성 관리가 Testcontainers 버전을 관리하도록 버전은 생략한다.

    dependencies {
        implementation("org.springframework.boot:spring-boot-starter-flyway")
        implementation("org.flywaydb:flyway-database-postgresql")

        testImplementation("org.springframework.boot:spring-boot-jooq-test")
        testImplementation("org.springframework.boot:spring-boot-testcontainers")
        testImplementation("org.testcontainers:testcontainers-postgresql")
    }

현재는 PostgreSQLContainer를 Spring Bean으로 등록하므로 JUnit의 @Testcontainers와
@Container 확장을 제공하는 testcontainers-junit-jupiter 모듈은 필요하지 않다.

기존 Mockito 테스트를 모두 제거하고 다른 테스트에서도 Mockito를 사용하지 않으면
다음 의존성도 제거할 수 있다.

    testImplementation("org.mockito.kotlin:mockito-kotlin:6.1.0")


6. Service + Repository 통합 테스트 구성
=======================================

@JooqTest는 전체 애플리케이션 대신 jOOQ와 DB 접근에 필요한 범위를 중심으로
Spring 테스트 컨텍스트를 실행한다. @Import는 테스트 대상인 사용자 정의
DiaryService와 DiaryRepository Bean을 명시적으로 추가한다.

@ServiceConnection은 PostgreSQLContainer의 접속 정보를 Spring Datasource에
자동으로 연결한다. 테스트에서는 application.yaml의 DB URL보다 이 정보가 우선한다.

현재 구현은 컨테이너를 Spring Bean으로 등록한다. 따라서 JUnit의 @Testcontainers와
@Container를 사용하지 않고 Spring Boot가 컨테이너 생명주기를 관리한다.

각 구성 요소의 역할은 구분해야 한다.

    PostgreSQLContainer
        실제 PostgreSQL Docker 컨테이너를 정의한다.

    @Bean 또는 @Container
        누가 컨테이너의 시작과 종료를 관리할지 지정한다.

    @ServiceConnection
        실행된 컨테이너의 접속 정보를 Spring Boot 설정에 연결한다.

@ServiceConnection 자체가 컨테이너를 생성하거나 시작하는 것은 아니다. 현재
방식에서는 @Bean으로 등록된 Container를 Spring Boot의 Testcontainers 생명주기
관리 기능이 시작하고 종료한다. @ServiceConnection은 컨테이너에서 JDBC URL,
사용자명과 비밀번호를 꺼내 JdbcConnectionDetails와 FlywayConnectionDetails를
구성한다. 따라서 application.yaml의 고정된 DB 접속 정보가 필요하지 않다.

과거에는 같은 연결을 위해 다음과 같이 속성을 직접 등록해야 했다.

    @DynamicPropertySource
    @JvmStatic
    fun databaseProperties(registry: DynamicPropertyRegistry) {
        registry.add("spring.datasource.url", postgres::getJdbcUrl)
        registry.add("spring.datasource.username", postgres::getUsername)
        registry.add("spring.datasource.password", postgres::getPassword)
    }

@ServiceConnection은 주로 이 DynamicPropertySource 코드를 대체한다.

JUnit이 컨테이너 생명주기를 관리하게 하려면 다음 조합을 사용한다.

    @Testcontainers
    @JooqTest
    class DiaryServiceIntegrationTest {
        companion object {
            @Container
            @ServiceConnection
            @JvmField
            val postgres = PostgreSQLContainer("postgres:18-alpine")
        }
    }

두 방식의 대응 관계는 다음과 같다.

    Spring Boot Bean 방식       @Bean + @ServiceConnection
    JUnit Extension 방식        @Testcontainers + @Container + @ServiceConnection

즉, @Bean과 @Testcontainers + @Container가 생명주기 관리 방식의 차이고,
@ServiceConnection은 두 방식 모두에서 Spring과의 접속 정보 연결을 담당한다.

    @TestConfiguration(proxyBeanMethods = false)
    class PostgresTestConfiguration {
        @Bean
        @ServiceConnection
        fun postgres(): PostgreSQLContainer =
            PostgreSQLContainer("postgres:18-alpine")
    }

    @JooqTest
    @Import(
        DiaryService::class,
        DiaryRepository::class,
        PostgresTestConfiguration::class,
    )
    @TestConstructor(autowireMode = TestConstructor.AutowireMode.ALL)
    class DiaryServiceIntegrationTest(
        private val diaryService: DiaryService,
    ) {

        @Test
        fun `일기를 저장하고 조회한다`() {
            val diary = Diary(
                title = "제목",
                content = "내용",
            )

            diaryService.createDiary(diary)

            val result = diaryService.findAll()

            assertEquals(listOf(diary), result)
        }
    }

@JooqTest 자체가 테스트를 트랜잭션으로 실행하므로 별도의 @Transactional 없이도
각 테스트가 끝난 뒤 롤백된다. 비동기 처리나 별도 트랜잭션을 사용하면 롤백만으로
정리되지 않을 수 있으므로 그때는 명시적인 데이터 정리 전략이 필요하다.


7. 가장 가치가 큰 커서 페이지 통합 테스트
===========================================

단순한 findAll 전달 테스트보다 커서의 누락과 중복을 검사하는 테스트가 중요하다.

예시 데이터가 ID 내림차순으로 다음과 같다고 가정한다.

    10, 9, 8, 7, 6

size가 2일 때 기대 결과:

    첫 번째 페이지 items: 10, 9
    첫 번째 nextCursorId: 9

    두 번째 페이지 items: 8, 7
    두 번째 nextCursorId: 7

검증해야 할 내용:
- 각 페이지 크기가 요청한 size 이하인가?
- 다음 데이터가 있을 때 hasNext가 true인가?
- 마지막 페이지에서 hasNext가 false인가?
- 페이지를 합쳤을 때 중복 ID가 없는가?
- 페이지를 합쳤을 때 누락된 ID가 없는가?

개념적인 테스트 형태:

    @Test
    fun `다음 페이지에서 일기가 누락되거나 중복되지 않는다`() {
        insertDiariesWithOrderedIds()

        val first = diaryRepository.findDiarySlice(
            CursorQuery(size = 2),
        )

        val second = diaryRepository.findDiarySlice(
            CursorQuery(
                cursorId = first.nextCursorId,
                size = 2,
            ),
        )

        val ids = first.items.map { it.id } + second.items.map { it.id }

        assertEquals(4, ids.size)
        assertEquals(4, ids.distinct().size)
    }

현재 쿼리는 id < cursorId를 사용하므로 nextCursorId는 응답에 포함된 마지막
항목의 ID여야 한다.

    val items = diaries.take(query.size)
    val nextCursorId = items.lastOrNull()?.id?.takeIf { hasNext }

size + 1로 가져온 감지용 항목의 ID를 커서로 사용하면 그 항목이 다음 쿼리의
id < cursorId 조건에서 제외되어 데이터 하나가 누락된다.

    // 잘못된 형태
    val nextCursorId = diaries.lastOrNull()?.id?.takeIf { hasNext }


8. 로컬 테스트 속도
===================

현재 통합 테스트의 전체 실행 사이클은 다음과 같다.

    테스트 JVM 시작
        -> PostgreSQL Docker 이미지 확인
        -> PostgreSQL 컨테이너 시작
        -> @ServiceConnection으로 DataSource 접속 정보 등록
        -> Flyway 마이그레이션 실행
        -> jOOQ DSLContext 생성
        -> DiaryRepository와 DiaryService Bean 생성
        -> 테스트 메서드마다 트랜잭션 시작
        -> 테스트 종료 후 트랜잭션 롤백
        -> 테스트 컨텍스트 종료 시 컨테이너 중지 및 제거

Testcontainers 테스트의 비용은 크게 세 부분이다.

    최초 실행: 이미지 pull + PostgreSQL 시작 + Spring context + Flyway
    이후 실행: 로컬 이미지 사용 + PostgreSQL 시작 + Spring context + Flyway
    같은 실행 안의 테스트: 기존 컨테이너와 Spring context 재사용

이미지를 처음 내려받은 이후에는 Docker 이미지 레이어가 로컬에 캐시되므로 pull
비용이 사라진다. 현재 PostgreSQLContainer는 Spring singleton Bean이므로 같은
ApplicationContext 안에서는 한 번만 시작한다. 테스트 메서드마다 컨테이너나
Flyway를 다시 실행하지 않고 트랜잭션만 새로 시작한다.

테스트 메서드 하나의 사이클은 다음과 같다.

    BEGIN
        -> diaryService.createDiary()
        -> DiaryRepository INSERT
        -> diaryService.findAll()
        -> DiaryRepository SELECT
    ROLLBACK

INSERT 결과는 같은 테스트 트랜잭션 안에서 SELECT할 수 있고, 테스트가 끝나면
ROLLBACK되어 다음 테스트에 데이터가 남지 않는다. UUID를 사용하므로 롤백되지
않는 DB sequence에 대해서도 현재는 신경 쓸 필요가 없다.

여러 테스트 클래스가 완전히 같은 Spring 테스트 구성을 사용하면 Spring Test의
context cache가 ApplicationContext와 그 안의 컨테이너 Bean을 재사용할 수 있다.
반대로 @Import, 프로파일, 테스트 속성 등이 달라져 context cache key가 달라지면
새 컨텍스트와 새 컨테이너가 시작될 수 있다. 테스트가 많아질 때 공통 테스트
애노테이션이나 설정 클래스로 구성을 통일하면 재사용률을 높일 수 있다.

@JooqTest가 전체 @SpringBootTest보다 빠른 이유는 웹 서버, Controller, MVC 등의
Bean을 띄우지 않고 DataSource, 트랜잭션, Flyway, jOOQ와 명시적으로 @Import한
Bean만 로딩하기 때문이다.

속도를 관리하는 방법:
- 단위 테스트와 통합 테스트를 별도 Gradle 태스크나 태그로 나눈다.
- 개발 중에는 관련 테스트만 실행한다.
- 커밋 또는 push 전에 전체 통합 테스트를 실행한다.
- CI에서는 항상 전체 통합 테스트를 실행한다.
- Spring 설정을 테스트마다 다르게 만들어 context cache를 깨지 않는다.


9. Testcontainers reuse 기능
============================

Testcontainers에는 종료 후에도 로컬 컨테이너를 유지하고 다음 테스트 실행에서
재사용하는 실험적 기능이 있다.

    // ~/.testcontainers.properties
    testcontainers.reuse.enable=true

    val postgres = PostgreSQLContainer("postgres:18-alpine")
        .withReuse(true)

주의:
- 공식적으로 실험적 기능이다.
- 컨테이너가 테스트 종료 후에도 남는다.
- 자동 정리와 네트워크 등 일부 기능에 제약이 있을 수 있다.
- CI 사용에는 적합하지 않다.

처음부터 reuse를 도입하지 말고 일반 Testcontainers의 실제 실행 시간을 먼저
측정한다. 속도가 개발 흐름을 방해할 때 로컬에서만 선택적으로 사용한다.


10. 권장 테스트 우선순위
========================

Diary 프로젝트에서는 다음 순서로 테스트 가치를 판단한다.

1. Repository 통합 테스트
   - 실제 PostgreSQL 쿼리와 jOOQ 매핑
   - 커서 정렬, 경계, 누락과 중복
   - hasNext와 마지막 페이지

2. Controller/API 테스트
   - 요청 파라미터 바인딩
   - 유효성 검증과 예외 응답
   - HTTP 상태와 JSON 응답 구조

3. 업무 규칙 단위 테스트
   - 의미 있는 계산이나 조건 분기가 생겼을 때 작성

4. 단순 Service 위임 단위 테스트
   - Mock 호출 검증뿐이라면 생략 가능


11. 최종 판단
=============

현재 DiaryServiceTest는 우선 유지하고, Service부터 PostgreSQL까지 실제 사용
경로를 연결하는 DiaryServiceIntegrationTest를 별도 파일로 추가한다. 통합
테스트가 SQL, 매핑, 마이그레이션과 페이지 경계를 검증하게 되면 완전히 중복되는
Mock 위임 테스트는 이후 제거할 수 있다.

권장 방식:
- 테스트 DB는 Testcontainers PostgreSQL을 사용한다.
- @JooqTest와 @Import로 DiaryService, DiaryRepository만 추가해 필요한 범위만 실행한다.
- 로컬 Compose 개발 DB는 테스트에 재사용하지 않는다.
- 컨테이너는 테스트 클래스 또는 JVM 실행 동안 한 번만 시작한다.
- CI와 로컬에서 동일한 테스트 구성을 사용한다.
- 단순 저장 및 조회보다 커서 누락과 중복 테스트를 우선한다.
- 실행 시간이 실제 문제가 된 뒤 로컬 전용 reuse를 검토한다.

기억할 원칙:

    테스트 종류나 계층보다 실제로 잡을 수 있는 버그를 기준으로 선택한다.
