추가 스택 제안

1. Detekt
Kotlin 의미 단위의 정적 분석을 CI에 추가하는 것을 권장한다. 현재 ktlint는 포맷을 잘 관리하지만,
복잡도·잠재 버그·불필요한 할당 같은 품질 규칙까지 다루지는 않는다. 처음에는 기본 규칙과
complexity 임계치만 적용하고, 기존 코드에 대한 baseline을 만든 뒤 점진적으로 강화하는 편이 안전하다.

2. Kover
서비스, 저장소, 페이지네이션의 회귀 방지를 위해 Kotlin 친화적인 커버리지 리포트와 최소 커버리지
검증을 추가할 수 있다. 단순 라인 비율보다 분기 커버리지 기준을 함께 두는 것을 권장한다.

3. Micrometer + Actuator
Caffeine의 recordStats 설정을 실제로 활용하려면 Actuator/Micrometer로 캐시 적중률, 제거 횟수,
DB 커넥션 풀과 HTTP 지연 시간을 노출하는 것이 좋다. 관측 결과 없이 캐시 크기와 TTL을 조정하면
메모리 사용량과 데이터 신선도 사이의 균형을 판단하기 어렵다.

4. JMH 또는 kotlinx-benchmark
문자열 미리보기나 목록 변환처럼 미세 최적화가 필요한 시점에는 추측 대신 벤치마크를 사용한다.
현재 규모에서는 운영 지표가 우선이며, 성능 병목이 확인된 코드에만 마이크로벤치마크를 추가하는
것이 유지보수 비용 면에서 적절하다.

5. Gradle configuration cache와 version catalog
configuration cache로 로컬·CI 빌드 준비 시간을 줄이고, libs.versions.toml로 플러그인 및 의존성
버전을 한곳에서 관리하는 것을 권장한다. 도입 전 모든 플러그인의 configuration cache 호환 여부를
CI에서 확인해야 한다.

6. CI 파이프라인
PR과 main 브랜치에 ktlintCheck, 정적 분석, 테스트, 빌드를 자동으로 실행하는 CI를 추가한다.
개발자의 로컬 환경에 의존하지 않고 깨끗한 환경에서 검증해야 하며, 실패한 단계와 로그를 쉽게 확인할 수
있도록 구성한다. Flyway와 jOOQ 코드 생성까지 필요한지 빌드 단계별로 명확히 구분한다.

7. 테스트 피라미드 정리
현재 도메인·서비스·통합 테스트가 있으므로 각 테스트가 어떤 위험을 검증하는지 정리한다. 순수한
도메인 규칙은 빠른 단위 테스트로 검증하고, jOOQ·PostgreSQL·캐시 동작은 통합 테스트로 검증한다.
같은 동작을 여러 계층에서 중복 검증하는 테스트는 줄여 전체 실행 시간을 관리한다.

8. 페이지네이션 계약 테스트
커서 페이지네이션에 대해 첫 페이지, 다음 페이지, 마지막 페이지, 빈 결과, 잘못된 size를 검증한다.
페이지 사이에 중복이나 누락이 없는지 확인하고, 데이터가 추가되는 상황에서도 UUID v7 정렬과 커서의
동작이 안정적인지 테스트한다. API 응답에서 nextCursorId를 어떻게 전달할지도 계약으로 고정한다.

9. 페이지네이션 정렬 기준 재검토
현재 UUID v7의 ID 순서를 정렬 기준으로 사용하고 있으므로, UUID 생성 방식이 바뀌면 페이지네이션도
영향을 받는다. ID 순서를 계속 사용할지, created_at과 ID를 함께 사용하는 복합 커서로 바꿀지 결정하고
그 이유를 문서화한다. 동일한 시각의 레코드가 있을 때도 순서가 결정적이어야 한다.

10. 캐시 일관성 정책
현재 diary slice 캐시는 생성 시 allEntries=true로 비운다. 수정·삭제 기능이 추가될 때도 모든 관련
페이지가 무효화되는지 보장해야 한다. 캐시를 비우는 시점을 트랜잭션 커밋 이후로 할지, 실패한 트랜잭션에서
캐시가 잘못 비워져도 허용할지 정책을 정한다.

11. 캐시 키와 직렬화 검증
CursorQuery가 캐시 키로 사용되는 현재 방식이 파라미터 변경과 동일성 비교에서 안전한지 테스트한다.
캐시 키에 사용자나 테넌트 같은 범위 정보가 추가될 가능성이 있다면 키 구조를 명시적으로 정의한다.
애플리케이션을 여러 인스턴스로 확장할 경우 로컬 Caffeine 캐시의 한계와 분산 캐시 필요성도 검토한다.

12. 캐시 용량과 제거 정책
Caffeine의 최대 크기, TTL, idle 만료 여부를 실제 조회 패턴에 맞춰 정한다. 무제한 캐시를 피하고,
메모리 사용량이 증가할 때 어떤 항목이 제거되는지 확인한다. 캐시가 데이터베이스보다 느려지는 경우를
대비해 캐시를 끄고도 서비스가 동작하는지 확인한다.

13. 관측 가능한 캐시 지표
Micrometer와 Actuator를 도입할 경우 hit, miss, eviction뿐 아니라 캐시 로딩 시간과 데이터베이스
조회 지연 시간도 함께 측정한다. 캐시 적중률만 높이고 오래된 데이터가 제공되는 상황을 성공으로 오해하지
않도록 신선도와 오류율을 함께 관찰한다.

14. 데이터베이스 인덱스 검토
커서 조건과 정렬에 사용되는 컬럼의 인덱스를 migration으로 관리한다. 실제 실행 계획을 확인해 인덱스가
사용되는지 검증하고, 데이터가 증가했을 때 offset 방식보다 현재 커서 방식이 효과적인지 부하 테스트로
확인한다.

15. 데이터베이스 제약조건 강화
NOT NULL뿐 아니라 필요한 경우 문자열 길이, ID 형식, 중복 조건을 데이터베이스에도 표현한다.
애플리케이션 검증을 우회한 데이터가 저장되더라도 도메인 규칙이 깨지지 않도록 하고, 제약조건 위반을
사용자에게 의미 있는 오류로 변환한다.

16. 트랜잭션 경계 문서화
서비스 메서드의 readOnly 및 쓰기 트랜잭션 경계를 유지하되, 여러 저장소 작업이 추가될 때 어느 계층이
트랜잭션을 소유하는지 명확히 한다. 캐시 무효화와 데이터베이스 커밋 순서가 어긋날 때의 동작도 테스트한다.

17. Flyway 마이그레이션 재현성
로컬 데이터베이스에 직접 의존하지 않고 새 데이터베이스를 처음부터 생성하는 테스트를 CI에서 실행한다.
마이그레이션 파일을 수정하지 않고 새 버전으로 추가하는 규칙, 실패한 migration 복구 방법, 운영 배포 시
실행 순서를 문서화한다.

18. jOOQ 코드 생성 재현성
jOOQ 생성 코드가 현재 스키마와 항상 일치하는지 검증하는 Gradle 작업을 둔다. 생성 코드를 커밋할지,
빌드 시 생성할지 팀의 기준을 정하고, 생성 코드와 migration이 불일치할 때 CI가 실패하도록 구성한다.

19. 테스트 데이터베이스 전략
Testcontainers를 사용하는 통합 테스트에서는 PostgreSQL 버전을 운영 환경과 맞춘다. 컨테이너 재사용,
migration 실행 시간, 테스트 격리 방식을 정해 로컬과 CI의 결과가 달라지지 않게 한다.

20. API 입력 검증
컨트롤러에서 받는 size, cursor, title, content의 유효성 검증을 일관된 방식으로 적용한다. 도메인
생성자 검증과 HTTP 입력 검증의 책임을 구분하고, 잘못된 입력이 내부 예외 메시지를 그대로 외부에 노출하지
않도록 한다.

21. 오류 응답 표준화
현재 IllegalArgumentException을 400으로 변환하는 방식에서 한 단계 나아가 잘못된 요청, 리소스 없음,
중복 데이터, 서버 오류를 구분한다. ProblemDetail의 type, title, status, detail, instance 필드를
일관된 형식으로 제공하고 오류 응답을 API 테스트로 고정한다.

22. 로깅 정책
요청 ID 또는 trace ID를 로그에 포함해 하나의 요청을 추적할 수 있도록 한다. diary 내용처럼 민감하거나
길이가 커질 수 있는 값은 로그에 남기지 않고, 생성·조회·실패 이벤트에 필요한 식별자와 처리 시간만
구조적으로 기록한다.

23. 헬스 체크와 운영 엔드포인트
Actuator를 도입한다면 애플리케이션 생존 여부와 PostgreSQL 연결 가능 여부를 구분한다. Kubernetes나
컨테이너 환경에서 사용할 liveness와 readiness 기준을 정하고, 운영 엔드포인트가 외부에 불필요하게
노출되지 않도록 접근 범위를 제한한다.

24. 설정 외부화와 비밀 관리
현재 데이터베이스 접속 정보가 Gradle 설정과 배포 스크립트에 반복될 수 있으므로 환경별 설정을 정리한다.
비밀번호와 토큰은 소스 코드나 이미지에 포함하지 않고 환경 변수 또는 배포 플랫폼의 secret으로 주입한다.
local, prod 설정의 차이와 기본값도 문서화한다.

25. 배포 전후 검증
이미지 빌드 전에 테스트와 migration 검증을 완료하고, 배포 후에는 애플리케이션 상태·데이터베이스 연결·
핵심 API를 확인하는 smoke test를 실행한다. migration 실패 시 애플리케이션을 함께 배포할지 중단할지
배포 순서를 정한다.

26. graceful shutdown
진행 중인 HTTP 요청과 데이터베이스 작업이 끝날 시간을 확보한 뒤 애플리케이션을 종료하도록 설정한다.
컨테이너 교체나 배포 중 요청 손실을 줄이기 위해 readiness를 먼저 내리고 종료하는 순서를 확인한다.

27. 의존성 및 컨테이너 보안 검사
Gradle 의존성의 알려진 취약점과 Docker 베이스 이미지의 취약점을 CI에서 검사한다. Spring Boot,
PostgreSQL, jOOQ, Flyway의 업데이트를 정기적으로 검토하고, 자동 업데이트는 테스트 통과 후에만 반영한다.

28. API 문서와 예시
컨트롤러의 요청·응답·오류·커서 페이지네이션 형식을 OpenAPI 등으로 문서화한다. 특히 cursor가 UUID인지,
다음 페이지가 없을 때 어떤 값을 반환하는지, size의 허용 범위를 문서와 구현에서 동일하게 유지한다.

29. 동시성 테스트
동시에 같은 diary를 생성하거나 여러 요청이 같은 페이지를 조회하는 상황을 테스트한다. UUID 충돌,
캐시 로딩의 sync 동작, 데이터베이스 제약조건 위반, 트랜잭션 경합이 예상대로 처리되는지 확인한다.

30. 부하 테스트
데이터가 적은 개발 환경의 결과만으로 캐시와 페이지네이션을 판단하지 않도록 대표적인 데이터 규모를
정한다. 목록 조회의 응답 시간, 데이터베이스 커넥션 풀, 캐시 메모리, 동시 요청 처리량을 측정하고
성능 목표와 경보 기준을 문서화한다.

31. 계약 및 아키텍처 테스트
Controller가 Repository를 직접 호출하지 않고 Service를 통해 접근하는지, 도메인 계층이 Spring이나
jOOQ에 불필요하게 의존하지 않는지 자동으로 검사한다. 패키지 경계가 커졌을 때 의존성 방향이 무너지지
않도록 ArchUnit 같은 도구를 선택적으로 검토한다.

32. Kotlin 컴파일러 설정
현재 strict nullability를 사용하고 있으므로 Java API의 nullable 계약이 올바르게 반영되는지 확인한다.
불필요한 경고를 방치하지 않도록 CI에서 경고 정책을 정하고, 공개 API에 대한 명시적 타입·문서화 수준을
프로젝트 규모에 맞춰 결정한다.

33. 시간 처리 정책
created_at과 UUID v7 생성 시간의 기준 시간대와 정밀도를 명확히 한다. 테스트에서는 현재 시간을 직접
호출하지 않고 주입 가능한 Clock을 사용하면 경계 시각과 재현 가능한 테스트를 작성하기 쉽다.

34. ID 생성기 추상화 여부 검토
현재 UUID 생성기는 간단하므로 별도 추상화가 꼭 필요하지 않다. 다만 테스트에서 생성 결과를 고정해야
하거나 다른 ID 전략을 지원해야 할 때만 Generator 인터페이스나 Clock 주입을 도입한다. 미리 추상화해
복잡도를 늘리기보다는 실제 요구가 생겼을 때 추가한다.

35. 데이터 보존 및 삭제 정책
diary의 수정·삭제·복구 요구사항을 정하고, 물리 삭제와 soft delete 중 하나를 선택한다. 개인정보나
사용자 작성 콘텐츠가 포함될 가능성이 있다면 보존 기간, 백업, 삭제 요청 처리, 로그의 보존 범위를 함께
정의한다.

36. 동시 수정 및 멱등성
생성 API가 재시도될 수 있으므로 클라이언트 요청 ID나 멱등성 키가 필요한지 검토한다. 수정 기능을 추가할
때는 낙관적 잠금(version 또는 updated_at)으로 마지막 저장이 조용히 덮어써지는 문제를 방지할지 결정한다.

37. 입력 크기와 자원 제한
title과 content의 최대 크기, 요청 본문 크기, 페이지 크기, DB 커넥션 풀 크기를 명시적으로 제한한다.
비정상적으로 큰 요청이나 과도한 페이지 조회가 메모리와 데이터베이스를 고갈시키지 않도록 서버와 DB 양쪽에
방어선을 둔다.

38. 인증·인가 확장 지점
현재 단일 사용자 예제라면 인증을 성급히 추가할 필요는 없지만, 사용자별 diary로 확장할 계획이라면
모든 조회·수정·삭제 쿼리에 소유자 조건이 포함되는지 설계한다. 캐시 키에도 사용자 범위를 포함해야 하며,
인증 전후 API 계약을 분리한다.

39. 모니터링 알림 기준
지표를 수집하는 것에서 끝내지 않고 HTTP 5xx 비율, p95 지연 시간, 데이터베이스 풀 고갈, 캐시 miss 급증,
마이그레이션 실패에 대한 알림 기준을 정한다. 정상 범위와 대응 담당자를 운영 문서에 기록한다.

40. 성능 최적화 도입 기준
문자열 미리보기나 목록 변환 같은 코드에 최적화를 먼저 적용하지 말고 운영 지표로 병목을 확인한다.
JMH 또는 kotlinx-benchmark는 측정할 가치가 있는 병목이 확인된 경우에만 사용하고, 최적화 전후의
정확성과 메모리 사용량도 함께 비교한다.

41. 의존성 버전 관리 자동화
version catalog를 도입한 뒤 Dependabot 또는 Renovate로 업데이트 후보를 정기적으로 생성한다. 모든
업데이트를 자동 병합하기보다는 Spring Boot, jOOQ, Flyway, PostgreSQL 드라이버처럼 영향 범위가 큰
구성요소는 별도 검토와 통합 테스트를 거치도록 한다.

42. 개발 환경 문서화
PostgreSQL 실행, migration, jOOQ 생성, 테스트 실행, 애플리케이션 구동 명령을 한 문서에 정리한다.
새 개발자가 Docker Compose만으로 동일한 환경을 재현할 수 있는지 확인하고, 자주 발생하는 포트·자격증명
문제와 해결 방법도 함께 기록한다.

43. 우선순위 관리
모든 도구를 한 번에 도입하지 않고 정확성, 보안, 운영 가시성, 성능 순서로 나눈다. 현재 단계에서는 CI,
페이지네이션 계약 테스트, 캐시 무효화 테스트, migration 재현성, 오류 응답 표준화를 먼저 적용하고,
부하 테스트·분산 캐시·인증은 실제 규모와 요구사항이 생겼을 때 추진하는 것이 적절하다.
